- **Repositories can opt into a release immutability policy that keeps the bytes at every stored file path from changing** (#4812). Setting `release_immutability: "on"` on a local or staging repository makes the upload paths (the service-backed formats and the native format handlers' delete-then-reupload check; Incus and OCI tags are not covered yet) refuse different bytes at an already-stored path with the 409 `IMMUTABLE_RELEASE` error, whether the earlier upload is live or was deleted. That covers paths today's rules leave replaceable: a version-less Generic blob after a delete, or an unrecognised file under a Maven release version. Re-uploading identical bytes still succeeds. Files a format rewrites in place by design (`maven-metadata.xml`, the npm packument, APT `dists/` indexes) and everything under a Maven `-SNAPSHOT/` directory stay writable. `immutability_exclusions` takes `*` glob patterns that exempt any path with a matching segment, such as `nightly`, `latest` or `*-SNAPSHOT`.

  The policy is `off` by default, so no existing repository changes behaviour, and the always-on release rules apply either way. Both fields are on the repository create, update, get and list API and in the OpenAPI spec. Remote and virtual repositories accept only the defaults: a publish through a virtual repository uses the policy of the hosted member it lands in. The policy cannot be combined with `versioning_enabled`. Changing it takes the repository `admin` action, like every repository update. The `REPOSITORY_UPDATED` audit entry records the policy before and after in `release_immutability_change`, with `loosened: true` when the change switches the policy off or adds an exclusion.
