- **A release can now be blocked: revoked without being deleted or overwritten** (#4812). `POST /api/v1/repositories/{key}/releases/{coordinate}/block` (with the package `name` in the body, `{coordinate}` is the version and every file of it is covered; without one, it is the URL-encoded path of a single file) refuses every download of the release with `403` on every route that goes through the shared download gate, virtual-repository members included, until `POST .../unblock` lifts it. Both need a `reason` and the repository's `admin` action or an instance admin, and write a `RELEASE_BLOCKED` / `RELEASE_UNBLOCKED` audit row and a `release_blocked` / `release_unblocked` webhook. The refused download never says why, so an anonymous caller on a public repository cannot read an incident note. The reason is readable only through the authenticated `GET .../releases/{coordinate}/block`. A block is stored apart from quarantine, so a re-scan, a quarantine release and a trash restore cannot lift it. The bytes stay, so a re-publish over a blocked release is still refused with `IMMUTABLE_RELEASE`. Deleting or purging a blocked release is refused with `IMMUTABLE_RELEASE`, for instance admins too.
